Formats and token cost

Markdown Tables vs. CSV vs. JSON: Which Uses Fewer Tokens?

For a small flat dataset, CSV may be compact; Markdown makes headers visible, while JSON can name fields. Exact counts depend on the input and tokenizer.

There is no format that always uses the fewest tokens for a table. CSV can be compact for a plain rectangle of values, Markdown adds visible row and header separators, and JSON can represent named fields or nested records with braces, quotes, and keys. The tokenizer's vocabulary, the exact values, and how headers are represented all affect the count.

Choose a format based on the person or software that will read it. A short count advantage is not useful if the row-to-header relationship becomes ambiguous. For one small synthetic comparison with exact inputs and a named model-family selector, see how the sample counts were measured.

Markdown tables: visible labels for a reader

Markdown tables put a header row above the values and keep each row on its own line. A human can scan columns without a separate schema. This can be handy when a prompt asks for comparisons and the table has a modest number of columns.

Markdown table syntax adds pipes and a separator row. It also has limits: merged cells, nested groupings, and visual emphasis do not map cleanly to a simple grid. A conversion may preserve a supported table while simplifying complex layouts, so check headers, units, and footnotes against the original. See the table review guide.

CSV: concise rows, external header assumptions

CSV is often a natural interchange format for rectangular data. A header line can label the columns, and later rows contain values in the same order. For a small, flat table with short fields, it can be compact. Commas inside values, quotation marks, newlines, missing values, and encoding rules require care. If the prompt omits the header, positional meaning may be hard to recover.

When sending CSV to an AI chat, label the delimiter and explain how empty fields should be interpreted. Keep units and reporting periods in a column or an explicit note rather than relying on visual styling that CSV cannot carry.

JSON: named fields, more structure

JSON can name every property and represent nested objects or arrays. That makes it useful when a program validates fields or when values have a more complex structure than a flat grid. Repeated keys and punctuation add characters. An array of positional values may be shorter but depends on an accompanying column definition. A misspelled key can also create a different field instead of an obvious visual misalignment.

Do not assume that explicit JSON is always cheaper or easier for a person to verify. Select the shape that matches the downstream task, and validate the data if software will consume it.

Measure one controlled example

A fair comparison uses the same headers, rows, values, units, and status notes in every form. Hold that data constant, count each exact string with the same tokenizer, and record the model selector. Then separately test any transformation such as removing rows or changing verbose headers. Do not use one sample's result to estimate every table.

Token count is not the only cost. A model may receive a prompt instruction, conversation history, or files in addition to the table. The destination tool may also interpret files differently from pasted text. Check the specific model and interface. Fewer tokens do not prove that an answer will be correct.

Keep the table trustworthy

  • Attach each number to its row label and column header.
  • Keep units, currencies, and dates beside the values they qualify.
  • Use an explicit marker for "not stated" when an empty cell could mean several things.
  • Preserve source title, URL, and version or checked date when freshness matters.
  • Flag conflicting sources instead of merging them into a single value.
