Formats and prompt design

Markdown vs. XML: Comparing Two Ways to Structure AI Prompts

Markdown offers a lightweight document outline; XML can name boundaries explicitly. Neither syntax is a security mechanism by itself.

Markdown is a practical fit for readable prompt notes with headings, lists, and short examples. XML can make named sections and nested boundaries explicit, which may help when a prompt contains several distinct blocks or a downstream process expects tags. Both add syntax to the text, and token cost depends on the exact sample and tokenizer. There is no universal rule that one format always guides a model better.

It also matters whether you are formatting instructions, source material, a structured record, or an output contract. These are different roles. For token comparisons using fixed sample text, see the measurement article; the examples there are not a general Markdown-versus-XML benchmark.

Use Markdown when the document shape is enough

A heading can label a task or a source, while a list can break the request into readable constraints:

## Task
Summarize the requirements below.

## Source material
Use the quoted policy excerpt as reference.

This style is easy to type, review, and edit. It works well for ordinary prose, checklists, and a source note that a person wants to scan. If a heading hierarchy is shallow, XML opening and closing tags may be unnecessary ceremony.

Use XML when named boundaries help

Tags make a section's role visible in the text:

<task>Summarize the requirements below.</task>
<source_material>Use the quoted policy excerpt as reference.</source_material>

XML can be useful for multiple named fields, nested records, or an interface that expects structured tags. Closing tags can make the boundary explicit, but they also add characters. A tag name is just text unless the receiving model or software has instructions for how to interpret it.

Choose the boundary format carefully

Ask who will consume the input. A human editor may prefer Markdown. A system that validates a field set may prefer JSON or another defined schema. An AI prompt may use headings, XML-like tags, or a combination supported by that tool's own guidance. Keep labels simple and describe how each block should be used rather than assuming a tag has built-in behavior.

For a fair token test, represent the same instructions and source text in both formats. Keep names, wording, whitespace, and examples constant where possible. Change only the delimiters, record the selected model family, and measure the exact input. Do not compare a short Markdown prompt to an XML prompt that also contains extra instructions and then attribute the count to markup.

Tags do not make untrusted text safe

Wrapping a webpage excerpt in a <source> block can make the intended boundary clearer to a reader. It does not neutralize malicious or irrelevant instructions that might appear inside the source, guarantee that a model will ignore them, or replace permission checks. Tell the AI that the block is reference material and that its contents are not instructions to follow. Avoid sending sensitive content unless the destination is approved.

Similarly, a tag such as <trusted> does not make its contents trustworthy. Verify important facts against the original source and do not treat tags as access control.
