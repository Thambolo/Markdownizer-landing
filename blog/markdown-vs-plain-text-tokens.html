Formats and token cost

Markdown vs. Plain Text: Are the Extra Formatting Tokens Worth It?

Formatting uses characters, but the useful question is whether those markers preserve distinctions your task needs.

Plain text can be the leaner choice for a short, self-contained passage. Markdown adds markers for headings, lists, links, and code, so a particular Markdown prompt may tokenize differently from its plain-text equivalent. Those markers can also keep a section title, list item, or link destination distinguishable. Whether that trade-off is worthwhile depends on the source and question, not on a universal rule that formatted text is better or worse.

A small measured example can show how one tokenizer handles one sample, but it cannot establish a general savings rate or a response-quality result. The measurement guide records exact synthetic inputs and their counts so readers can reproduce the comparison.

What plain text leaves implicit

Imagine an excerpt with a title, two sections, and three requirements. In plain text, all the same words may remain, but the reader has to infer which lines are headings and which are list items. A blank line can suggest a boundary without naming what it means. A URL pasted beside a phrase may not be clearly attached to the words it supports.

That ambiguity may be harmless when a prompt contains one short paragraph. It can matter more when the source has nested requirements, multiple products, code snippets, or links to several references. Markdown can express some of these relationships with a small set of visible conventions:

## Requirements
- Preserve the reporting period.
- Mark missing values as unknown.

See [the source note](https://example.org/source).

The example is illustrative. It does not prove that an AI model will follow the requirements or verify the link.

What Markdown markers cost

Markdown is not free of syntax. A heading marker, list prefix, table separator, or link destination adds characters to the submitted text. Some tokenizers combine frequent punctuation patterns; others divide them into multiple tokens. A bullet point that costs little in one language or model family may behave differently in another. Compare the exact model or tokenizer you intend to use.

For an honest test, keep every word and destination the same, remove only the formatting syntax, and record both token and character counts. Then check whether the unformatted version still communicates the same hierarchy. Do not edit down the Markdown sample and then attribute the entire difference to the format.

Decide whether the structure earns its place

  • Use plain text for a short paragraph or quotation whose meaning is already clear.
  • Keep Markdown headings when section boundaries determine which rule, result, or caveat applies.
  • Keep list markers when items are separate requirements, choices, or steps.
  • Keep link labels and destinations when you need to return to a source, while remembering that a pasted link is not proof the AI visited it.
  • Keep code fences when indentation or command boundaries matter to review.

Do not preserve formatting just because it is available. Also do not strip structure solely to lower a count if that makes a critical relationship harder to verify. A few extra markers can be a reasonable trade when they prevent you from misreading the input, but token count alone cannot prove that a model will perform better.

Measure and review the actual prompt

Use the OpenAI Tokenizer or the destination tool's own guidance for its supported model. Record the selector shown in the interface, date, and exact sample. The popup character count in Markdownizer is not a model token count. For advice on which material to include, see how much source material to put in a prompt.

Markdownizer converts an open webpage to Markdown; it is not a general plain-text or HTML file converter. If its output includes useful structure, review it against the page before copying. For a wider look at structure versus ordinary clipboard behavior, read Markdown vs. copy-paste.
